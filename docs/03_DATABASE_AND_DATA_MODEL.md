# Database and data model

PostgreSQL 17 is authoritative. SQLAlchemy uses `postgresql+psycopg`. Never use SQLite for integration/concurrency tests.

## Conventions

`id` means UUID, generated by the application (`uuid4` for live rows, `uuid5` for seed rows). All tenant-owned tables below have `workspace_id UUID NOT NULL`, `created_at timestamptz NOT NULL DEFAULT now()` and `updated_at timestamptz NOT NULL DEFAULT now()` unless marked immutable. Each has PK `(workspace_id,id)` except explicitly stated natural-key tables. All tenant foreign keys include `workspace_id`; a naked UUID foreign key is forbidden. References to a business code in examples resolve to UUIDs, never substitute strings for UUID fields.

`text` fields are bounded in Pydantic; core identifiers use SQL `varchar` bounds. Monetary amounts are nonnegative `bigint` paise; quantities are integer units. Ratios/forecasts use `numeric(18,6)`. API exposes monetary integers, not floating-point currency. Currency is constrained to `INR`. Dates use retailer timezone `Asia/Kolkata`; event timestamps use UTC. `version integer NOT NULL DEFAULT 1` is optimistic concurrency version where listed. Every mutation increments it, including allocation changes to inventory rows.

All fields are NOT NULL unless suffixed `?`. JSON is `jsonb` and must validate against the associated API schema; JSON is never a substitute for relational stock/order links. Enumerations are text CHECK constraints so migrations remain straightforward. Soft deletion uses `active` on catalog/reference records. Business transactions are never hard deleted outside an explicitly scoped synthetic workspace reset.

Untyped field conventions in the tables: `*_id` is a tenant UUID FK unless explicitly global; `actor_uid` is varchar(128); `*_date`, `window_start/window_end/start_date/end_date` are date; `*_at`, `event_time` and `completed_at` are timestamptz; `*_minor` is bigint paise (observed/estimated contribution may be signed); `*_days`, `quantity` and `received_quantity` are integer; `source_ref/permission_ref/keyword/name/explanation` hashes and version labels are text unless bounded above. Ratios use numeric(18,6). Every FK named by an entity exists, including optional recommendation references added after table creation.

## Inventory semantics

At real UTC time `t`, active quantity is the sum of allocations with state ACTIVE and either no expiry or `expires_at > t`. HOLD expiry always uses wall-clock time, not the fixed scenario date.

`	sellable_physical = on_hand - blocked`

`ATP = sellable_physical - active_hold - active_order - active_transfer`

The persisted invariant is `ATP ≥ 0` under row locks. A negative query result is a reconciliation error, not something to conceal by clamping. Public API refuses a new allocation and logs `INVENTORY_INVARIANT_FAILED`. Incoming POs/transfers are **not ATP** before physical receipt. Dashboard separately displays confirmed future incoming units. Expired HOLD rows contribute zero even before a cleanup job.

## Required state transitions

| Operation | Preconditions and locks | Atomic result |
|---|---|---|
| Create hold | Quote ≤5 minutes old, same actor, requested option exists; inventory row lock; current constraints and stock valid | HOLD ACTIVE, 15-minute expiry; inventory version++ |
| Convert hold to order | Lock hold then inventory; hold ACTIVE and unexpired; actor matches | Order CONFIRMED; same allocation becomes ORDER with no expiry; no second reservation; inventory version++ |
| Cancel hold/order | Owner; order not shipped/fulfilled | Release allocation; order CANCELLED; version++ |
| Fulfil pickup | Associate/manager, CONFIRMED pickup | `on_hand-q`, allocation CONSUMED; order FULFILLED; sale movement, daily sales and outcome |
| Dispatch shipment | Associate/manager, CONFIRMED shipping | `on_hand-q`, allocation CONSUMED; SHIPPED; sale movement and daily sales; observed completion outcome waits for DELIVERED |
| Deliver shipment | SHIPPED | DELIVERED and outcome; no extra stock or sales change |
| Approve transfer | Manager; current recommendation; source ATP and donor protection rechecked | Transfer APPROVED, source TRANSFER allocation ACTIVE; neither balance moves yet |
| Dispatch transfer | APPROVED | Source `on_hand-q`, allocation CONSUMED; IN_TRANSIT; TRANSFER_OUT movement |
| Receive transfer | IN_TRANSIT | Destination `on_hand+q`; RECEIVED; TRANSFER_IN movement/outcome; no source decrement again |
| Approve PO | Manager; current recommendation; MOQ/pack/capital constraints | PO APPROVED with expected date; no stock balance change |
| Receive PO | APPROVED | Destination `on_hand+q`; RECEIVED; PO_RECEIPT movement and outcome |
| Receive return | Original order fulfilled/delivered; remaining returnable qty sufficient | `on_hand+q` and `blocked+q`; RETURN_RECEIPT; refund is accounting simulation |
| Restock return | RECEIVED and inspection passed | `blocked-q`; RETURN_RESTOCK; RESTOCKED; ATP rises only now |
| Damage return | RECEIVED and inspection failed | `on_hand-q` and `blocked-q`; RETURN_DAMAGE; DAMAGED; no ATP increase |

Return receipt increments `daily_sales.returned_units` once at the original order's `demand_location_id` on the current scenario date and writes negative observed contribution of `refund_minor - quantity×unit_cost_minor` (negative sign applied). Damaged stock additionally reduces contribution by cost of damage decision, recorded in audit/outcome adjustment; use event_type=RETURN_DAMAGED with the same return reference_id, zero observed_units and negative quantity×unit_cost_minor. The unique event_type/reference_id pair prevents duplicates. Lock the parent order when creating returns so simultaneous requests cannot exceed its returnable quantity. Never forecast negative demand from returns.

In-transit stock conservation: network on_hand + dispatched-not-received transfer quantity remains constant through transfers, ignoring sales/receipts. Once dispatched, transfer cancellation is unsupported; reverse movement requires a new reviewed transfer. PO/transfer partial receipt is later scope; reject partial quantities with 422 instead of silently implementing it.

## Demand attribution across channels

Every order has a demand location id distinct from its stock origin. Pickup uses the pickup store. Shipping maps destination_code to its unique locality STORE (INDIRANAGAR→S1, WHITEFIELD→S2, JAYANAGAR→S3), even when fulfillment originates at DC1 or another store. Fulfillment/dispatch updates gross daily sales at demand_location_id; returns update returned_units there. Stock movements always affect the physical origin/return location. This avoids treating DC shipping as independent DC demand or counting one shipment at both origin and destination. Seed orders use demand_location_id=origin store.

## Indexes

Create B-tree indexes for allocations `(workspace_id,product_id,location_id,state,expires_at)`; orders `(workspace_id,actor_uid,created_at DESC)`; daily sales `(workspace_id,location_id,business_date,product_id)`; intent events `(workspace_id,location_id,business_date,category_id)`; recommendations `(workspace_id,status,created_at DESC)`; forecasts `(workspace_id,run_id,product_id,location_id,forecast_date)`; incoming PO (workspace_id,destination_location_id,status,expected_date) and transfers equivalent; membership UID; audit entity/date. Product search for 24 SKUs uses parameterized ILIKE + typed fact filters; no vector index or full-text tuning needed. Unique indexes enforce seed code and idempotency keys.

## Migrations and seed ownership

Revision `0001_core`: identity, catalog and inventory. `0002_commerce`: intents, quotes, allocations, orders, movement and operational records. `0003_intelligence`: sales, signals, policies, forecasts and recommendations; add deferred FKs. `0004_audit_limits`: audit/idempotency/quotas, indexes, runtime grants. Downgrade in local disposable DB only; production rollback uses compatible app revision, not destructive schema downgrade.

Migration principal owns schema. Runtime principal gets SELECT/INSERT/UPDATE/DELETE on workspace data as needed for synthetic resets; append-only ledger/audit tables get no UPDATE outside the owner maintenance/reset job. Runtime never gets CREATE/ALTER/DROP. Reset is an owner maintenance command or authenticated demo workspace reset implemented by deleting the entire workspace via explicitly permitted cascading function; do not grant blanket ledger mutation. The chosen MVP reset route is **owner maintenance job only**; the UI starts a new session only after its prior workspace expires. E2E resets use disposable databases or owner test fixtures.

Seed rules and representative records are authoritative in [13_SYNTHETIC_DATASET.md](13_SYNTHETIC_DATASET.md). A template workspace is read-only to runtime. `POST /demo/sessions` creates a new workspace by copying the seed specification through service inserts, not copying template UID/membership. UUID5 includes new workspace ID. One transaction succeeds completely or leaves no workspace. Fresh seeding never overwrites live workspace state.
